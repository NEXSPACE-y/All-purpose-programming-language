# Static native dependency and implementation audit

The fixed Windows PHP8.5.12 oracle contains36 extension DLLs. Their PE tables require985 unique php8ts.dll names, including59 DATA imports. The frozen own original and callback cores export54/60 names respectively, comprising the **same29 PHP ABI names** and25/31 ALL-specific control/probe names. Among this local extension set, only dl_test has all its normal named core imports present. These are counts of names, **not compatibility percentages or runtime passes**.

`static01/inventory.json` contains each DLL's file hash, PE machine, normal/delay imports, statically decoded module entry and missing-name list for both own cores. Existing dumpbin produced41 successful read-only inspections; its raw stdout/stderr and commands are retained. An independent PE parser cross-checks each imported PHP symbol against dumpbin output. No extension/stock PHP was loaded or executed, no tool was installed, and every input hash was unchanged.

`source02/source-audit.json` distinguishes present narrow implementations, real DATA function pointers, a partial handler table with explicit unsupported paths, missing exports, private unsupported handlers and unassigned/absent value machinery. All985 requirements have a per-core classification and importing-module list. The29 present PHP names have actual source definitions; no standalone dummy/no-op export was observed among them. That does not make them complete: table formatting differs, scalar coercion is selected, registration is partial and object/property/value ownership is incomplete. A legitimate text-mode no-output function must also be distinguished from a dummy stub.

`source02/modules.csv` is the compact per-module map. source01/failure.json preserves the initial static classifier's failure to recognize a real DATA initializer; source02 fixes that finder only, without changing a binary, implementation or fixture.

The principal ownership gap is concrete: copy_value retains only strings; array/object copies are shallow, and destroy does not implement a general recursive/reference/resource/object lifecycle. Populated arrays and non-scalar return tags are explicitly rejected. The object handler table registers metadata and selected handlers but refuses property/dimension/cast/enumeration execution. Resource registries and general GC are absent. Current module/TLS lifecycle is a selected single-module profile with failure-rollback and foreign-thread-unload work remaining.

[NEXT_BATCHES.md](NEXT_BATCHES.md) specifies additive message-length and module-info corrections, a four-missing-name gettext candidate, and staged array/reference/object/resource/ownership/lifecycle work with acceptance gates. It uses pinned8.5.12 local source/header contracts as reference only, within approved native option A. No source implementation was adopted or core changed. Linux binaries/SAPI execution and absent third-party builds remain separate unmeasured work.
