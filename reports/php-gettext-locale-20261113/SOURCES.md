# Separate locale selection from observed catalog translation

This is a read-only source investigation, not a translation result. The exact GNU libintl version/configuration embedded in the pinned PHP8.5.12 gettext binary has not been established. Upstream source versions below explain controls to measure; they are not substitutes for executing that binary.

[GNU gettext locale environment documentation](https://www.gnu.org/software/gettext/manual/html_node/Locale-Environment-Variables.html) documents locale categories and the environmental priority relationships. [GNU gettext language-list documentation](https://www.gnu.org/software/gettext/manual/gettext.html) describes LANGUAGE selection and the C-locale exception. A CRT locale setter succeeding therefore does not by itself demonstrate selection or loading of the intended message catalog.

[GNU gettext v0.26 dcigettext.c](https://raw.githubusercontent.com/autotools-mirror/gettext/v0.26/gettext-runtime/intl/dcigettext.c), lines1385-1438, selects the message locale, bypasses LANGUAGE for C and C followed by an encoding suffix, and otherwise considers the language preference. Catalog selection and lookup occur separately. This makes C.UTF-8 an explicit negative control. [The v0.22.5 source](https://raw.githubusercontent.com/autotools-mirror/gettext/v0.22.5/gettext-runtime/intl/dcigettext.c), lines1488-1539, has a narrower exact-C check. The version difference is a reason to measure the actual extension, not assume that its behavior matches either source tag.

[GNU gnulib localename-environ.c](https://raw.githubusercontent.com/coreutils/gnulib/master/lib/localename-environ.c), lines23-45, selects nonempty LC_ALL, then the requested category, then LANG. [Its current Windows locale handling](https://raw.githubusercontent.com/coreutils/gnulib/master/lib/localename-unsafe.c), lines2717-2782, includes a CRT-to-locale conversion for supported native categories and an environmental fallback path. These master-branch files are explanatory current source, not an identified dependency pin of the actual binary.

[Microsoft's setlocale contract](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/setlocale-wsetlocale?view=msvc-170) documents application/thread locale state and the supported CRT category set. LC_MESSAGES is not in that native category list. The new oracle should query actual CRT LC_ALL/LC_CTYPE state and record the PHP LC_MESSAGES constant separately, without assuming that a CRT locale result equals the locale used by GNU message lookup. Changes remain confined to each child process.

The approved local PHP archive's `ext/gettext/config.w32` links libintl; it does not identify the library version. `ext/standard/string.c:5005-5068` shows PHP's Windows locale setter/query path and its special handling of POSIX-style locale names. The existing controls continue to request the same accepted English_United States.utf8 CRT locale. New environmental controls use POSIX locale strings separately; they do not attempt locale installation.

A current preparation-process observation is LC_ALL=C.UTF-8 and LANG=C.UTF-8, with LC_MESSAGES/LANGUAGE absent. Earlier51 process environments were not fully captured, so this is a hypothesis for those historical identity results. The new controls explicitly record the five locale variables before each child starts and inside PHP, its requested/returned CRT locale, binding result, unchanged copied-MO hash and actual singular/plural bytes. Original51 fixtures and MO remain frozen. Translation identity is never credited as catalog translation.
